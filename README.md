# СтройКонтроль

Приложение: https://sayaha89.github.io/stroykontrol/

`index.html` — основное приложение с Supabase Authentication и общей базой объектов.
`index2.html` перенаправляет старые ссылки на основную версию.
Запускайте по HTTPS через GitHub Pages, а не как локальный файл.

## Настройка Supabase

В коде используется публичный publishable key. Secret key и service_role нельзя размещать в браузере или этом публичном репозитории.

Требуются таблицы:

- `objects`: `id` (primary key с автоматически создаваемым значением), `name`, `address`, `deadline`, `status`.
- `admins`: `user_id` (UUID пользователя из Authentication, уникальное значение).

Сотрудников создаёт администратор в Supabase Authentication; самостоятельная регистрация отключена. Для доступа добавьте UUID сотрудника в `admins` через административный интерфейс Supabase.

На обеих таблицах необходимы серверные политики RLS. Пользователь должен иметь возможность прочитать собственную запись `admins`. Только разрешённые пользователи должны читать, добавлять и удалять `objects`. Проверка в интерфейсе дополняет RLS и не заменяет его. Не открывайте таблицы для `anon` ради устранения сообщения об ошибке.

## Проверка

1. Откройте основную ссылку — появляется форма входа.
2. Войдите разрешённым аккаунтом; проверьте загрузку объектов.
3. Создайте тестовый объект и убедитесь, что он виден после обновления страницы и на другом устройстве с разрешённым аккаунтом.
4. Удалите тестовый объект и выйдите.

Прежняя версия `index.html` сохраняла объекты только в localStorage устройства (`stroykontrol_objects`). Эти записи не удаляются исправлением и автоматически в базу не переносятся.

## Восстановление пароля

В приложении доступны «Забыл пароль» и форма нового пароля. Для проекта Supabase в Authentication → URL Configuration задайте:

- Site URL: `https://sayaha89.github.io/stroykontrol/`
- Redirect URLs: `https://sayaha89.github.io/stroykontrol/?recovery=1`

Настройка URL находится в Supabase и не меняется публикацией HTML в GitHub.
Письма восстановления должны отправляться через настроенный SMTP либо разрешённый для этого адреса почтовый сервис Supabase.
Пароль панели Supabase с входом через GitHub и пароль пользователя приложения — разные учётные данные.
Восстановление проверяет действующую авторизованную сессию прежде, чем разрешить смену пароля. Проверка доступа к объектам выполняется после смены пароля.

Проверки логики: `node tests/auth.test.cjs`. Они используют модель Supabase и DOM; не заменяют проверку реальных политик RLS и доставки писем.

## Ежедневный контроль и сотрудники

- Руководитель создаёт сотрудников в разделе «Сотрудники» (ФИО, почта, начальный пароль от 12 символов), назначает их в карточке объекта и лично передаёт данные входа.
- Сотрудник видит только назначенные ему объекты, может добавлять ежедневные отчёты и свои фотографии. Вход по общей ссылке приложения. Пароль можно изменить после входа.
- Доступ к объекту задаётся выбором учётной записи сотрудника. Текстовое поле «Ответственный» само по себе прав не выдаёт.
- Отчёт содержит дату, выполненные работы, следующий план, проблемы, нужные решения и фото. Фотографии хранятся в приватном bucket `daily-photos`; ссылки просмотра действуют один час.
- До 8 фото в одной загрузке; фото уменьшаются до 1800 пикселей по длинной стороне и конвертируются в JPEG в браузере. Если браузер не читает исходный формат, выберите JPEG/PNG.
- При сбое фото текст отчёта сохраняется; фото можно добавить к своему отчёту отдельно. Объект с отчётами нельзя удалить — завершите его через статус.
- Экран контроля показывает отчёты назначенного ответственного за выбранную дату. Флажок «Нужна помощь» означает наличие текста в проблемах или требуемом решении, а не подтверждённую просрочку решения.

Схема и политики: `db/daily-control.sql`. Серверная функция создания сотрудников: `functions/create-employee.ts`; секретный ключ берётся только из серверного окружения Supabase. Пользовательский JWT и членство в `admins` проверяются до вызова Auth Admin API.

Проверки: `node tests/auth.test.cjs` и `node tests/employees.test.cjs`.
